USDC on Arc Working prototype, September 2026

An invoice is text that a different company wrote. Your agent reads it. Your contract pays.

Warrant lets an AI agent operate a business's accounts payable in USDC. The agent reads invoices and proposes payments. It cannot make one. A small checker program makes the decision. An escrow contract on Arc releases the money, and it accepts only an authorization that it can examine. Prompt injection, changed bank details and duplicate invoices do not pass.

Where every fact comes from

The checker accepts three kinds of fact. A fact that it cannot put in one of these kinds is unknown. An unknown fact never becomes a payment.

Signed

The registry signs the wallet address of each vendor. The buyer signs the purchase order, its ceiling and its lines. A reviewer can sign that the work is acceptable.

keys the buyer approved

Derived

The parser reads the amount, the seller tax identifier, the invoice number and the line texts from the invoice bytes. It rejects external entities. It limits the size and the depth.

a function of the document

Checked

The model can label a line. The checker admits the label only when it matches a signed purchase order line, or a term from the buyer's own list.

re-verified, or unknown

Fields that select must never come from the text. Fields that quantify can.

The checker gives one of three answers

A fixed evaluator turns the facts into a decision. Verus proves that the evaluator agrees with its specification. It also proves the property that the design needs: when facts are unknown, Allow holds only if it holds for every completion of those facts. The proof has sixteen obligations. It rejects fourteen deliberate bugs, which include a bug that treats Ask as Allow.

Allow

Allow produces an authorization of fourteen words. The authorization binds the policy, the invoice, the evidence, the recipient, the amount and the order. No other result produces one.

Deny

There is no authorization to send. The checker refuses a payment above the purchase order ceiling. The contract refuses it again against live state.

Ask

The checker returns its reasons and signs nothing. A wrong label, an unreadable format or an unknown currency gives this result. Ask is an escalation path. It is not a failure.

Three ways an invoice settles

An escrow contract on Arc holds the buyer's USDC, one purchase order at a time. The contract has no administrator, no policy setter, no pause control and no withdrawal function.

The vendor accepts the terms of the order before delivery. After that, the buyer can recover only the money that nobody paid, and only after the deadline. Each invoice pays one time across all three paths. The key is the seller tax identifier and the invoice number.

Path When it applies Who authorizes Time to settle
settleSigned The amount is below the proof threshold of the order. The signing service that the buyer named. It runs the same checker against the order that it reads from the chain. 0.04 s, measured
settle The amount is at or above the threshold. A proof that the checker ran on those exact bytes. The contract verifies it against a pinned program. Minutes, asynchronous
settleApproved The checker returned Ask. The buyer, with the buyer's own key, inside the ceiling and the deadline of the order. One transaction

The proof path does not delay a small payment. The wait is latency and not risk, because the contract reserved the money when the buyer funded the order.

What a stolen signing key gives an attacker

It gives no way to send money elsewhere. The contract fixes the recipient when the buyer funds the order. A signature that names a different address fails. Division of a payment into small parts does not help, because the allowance limits the total and not each payment.

An attacker with no accomplice gains nothing. An attacker with a dishonest vendor can take the remaining ceiling or the signer allowance, whichever is smaller. This applies only to the orders that name that key. The buyer had already committed that money to that vendor.

The buyer revokes the signer for one order with one transaction. Proofs continue to settle. An order cannot name its own vendor as the signer.

What is proved, what is tested, what is assumed

These three words mean different things. This page keeps them apart, because a claim of proof that the code does not support is worse than no proof at all.

Proved
The rule evaluator agrees with its specification. Allow and Deny hold for every completion of the unknown facts. Verus, 16 obligations, 14 of 14 deliberate bugs rejected
Tested
The parser, the checker, the signing service and the escrow. The tests include fuzz cases on the ceiling and the allowance, signer isolation between orders, and removed-check experiments on each settlement path. 43 Rust tests, 57 Solidity tests
Assumed
An honest signing service for each order. Honest registry keys and buyer keys. A standard ERC-20 token. A correct proof verifier. The checker examines what an invoice says, not whether it is true. The ceiling of the order bounds a dishonest vendor.
Known limits
Universal Business Language and US dollars only. Every other format gives Ask. The escrow bounds each order. There is no budget for each category or for each period.

Showcase: an agent buys GPU time and transcribes audio

The showcase shows Warrant with a real purchase. A buyer agent rents a one-hour GPU container from a seller. The container runs a faster-whisper transcription worker. The buyer sends audio to it and receives the text with timestamps. The buyer agent holds no key that can pay. A local guardrail program holds the keys and the spending cap.

How a purchase runs

  1. Quote. The agent asks the seller MCP server for a GPU and a price. The seller returns a proposal with a task_id. A quote moves no money.
  2. Policy check. The buyer guardrail checks the budget cap and the lease length. It derives the policy hash. It then funds TaskEscrow on Arc.
  3. Acceptance. The seller reads the order from the chain and accepts it. The buyer cannot cancel after this step. The seller starts the container on io.net.
  4. Health check. The buyer calls /health on the container with the worker token. The buyer then signs an acceptance statement with its own key.
  5. Settlement. The checker evaluates the evidence. It produces the authorization journal. The escrow releases the USDC to the seller.
  6. Transcription. The buyer posts audio to /job and reads the result from /job/<id>. The lease lasts one hour.

State of the showcase on 17 October 2026

The seller for Arc mainnet (chain ID 5042) is live at https://seller.mnemonik.xyz/mcp. It needs HTTP basic auth. The operator gives the credential. The full purchase path on mainnet has not run with money yet. The seller uses a test-double verifier that checks no signature, so the buyer trusts the seller. The cap is 1 USD for each deal.

A separate solver bounty settled on mainnet on 16 October 2026 with a real Groth16 proof.

How to run it as a buyer

You need a Rust toolchain, Python 3, Node.js, an MCP client such as Claude Desktop or Cursor, and an Arc wallet with a little USDC. Run every command from the root of the policy-execution repository.

  1. Build the checker. The guardrail needs the compiled binaries.
cargo build --release -p warrant-host
python3 -m venv .venv
.venv/bin/pip install -r showcases/ionet_arc/requirements.txt
  1. Make your own acceptance key. Never use a key that another person gave you.
mkdir -p showcases/ionet_arc/.keys
(umask 077 && openssl rand -hex 32 > showcases/ionet_arc/.keys/buyer_acceptance.key)
  1. Write your manifest. Copy showcases/ionet_arc/config/manifest.yaml to a file outside git. Set chain_id: 5042, rpc_url: https://rpc.mainnet.arc.io, the escrow, verifier and token addresses from the README, your own buyer_address, and max_budget_usd: 1.00. Add your public acceptance key to a copy of mainnet-public_keys.yaml.
  2. Add the two MCP servers to your client. The guardrail runs locally over stdio with your wallet key file. The seller runs remotely. Put the basic-auth value in the environment variable SELLER_AUTH. Do not paste the password into a chat.
{
  "mcpServers": {
    "buyer-warrant-guardrail": {
      "command": "/path/to/repo/.venv/bin/python",
      "args": ["-m", "showcases.ionet_arc.buyer_mcp_server",
               "--transport", "stdio",
               "--manifest", "/path/to/your/manifest.yaml",
               "--key-file", "/path/to/your/buyer.key"]
    },
    "seller-transcription-service": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://seller.mnemonik.xyz/mcp",
               "--header", "Authorization:${SELLER_AUTH}"],
      "env": { "SELLER_AUTH": "Basic <base64 of user:password>" }
    }
  }
}
  1. Ask the agent. Restart the client and open a new chat. For a quote only, say: "Use the seller-transcription-service tools to request a quote for a transcription task with a maximum of 1.00 USD. My customer address is <your wallet>. Do not fund or accept anything." To buy, ask it to deploy and to transcribe your audio file. Extract the audio first from a video: ffmpeg -i video.mp4 -vn audio.mp3.

How to run the seller yourself

To host a seller, start the seller MCP server. It reads the same manifest. It refuses to start when the RPC does not answer eth_chainId.

.venv/bin/python -m showcases.ionet_arc.seller_mcp_server --host 0.0.0.0 --port 8000
# add --local-server --ssh-host <host> to deploy the container over SSH and Docker
.venv/bin/python -m unittest showcases.ionet_arc.test_pilot -v   # offline tests

The transcription worker has its own repository: mnemonik-xyz/transcription. The full runbook, the contract deployment steps and the operator notes are in showcases/ionet_arc.

What this showcase does not prove

The seller gives no hardware attestation. The buyer cannot confirm the GPU model. The buyer confirms only that the container answers with the secret token. The shared basic-auth credential lets any holder call every tool. Hand it out only to people you trust.

Where this goes next

Everything above runs on a local machine today. This includes real proofs and settlement on a disposable chain. Three stages separate that state from money that moves for a real business.

1
Deployment In progress

We put the same code on Arc testnet. Anyone can then open the transactions in a block explorer.

  • Set up an x86 machine with Docker for the prover. Record the reproducible program identifier that it builds.
  • Deploy a proof verifier. RISC Zero publishes none for Arc.
  • Deploy the escrow against that verifier and that program identifier.
  • Fund the deployer wallet and the buyer wallet with testnet USDC. Arc also uses USDC to pay for gas.
  • Run the signing service with the policy file, the signer key and read access to an Arc endpoint.
  • Confirm that the deployed escrow reports the expected token, verifier and program. Do this before you fund an order.
2
Full flow on testnet Next

We run the whole path on a public chain with invoices that we write. We fund an order. The vendor accepts it. A small invoice settles by signature. A large invoice settles by proof. An undecided invoice goes to the buyer. Each case gives a transaction that anyone can open in a block explorer. The invoices are synthetic. The contracts and the proofs are real.

3
First real payments Later

Then real vendor traffic starts. Two applications lead. The first is infrastructure that an agent buys for itself, which starts with a virtual server. The second is a financial workflow such as trading. Both contain small, repeated and well-specified payments.

The agent proposes. The checker decides. The chain pays, only within bounds.

Warrant is a prototype on Circle's Arc. The figures come from local runs that the repository records. They do not come from production traffic.
